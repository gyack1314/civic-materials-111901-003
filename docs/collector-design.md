# 采集端设计与安全纪律

采集端（`collector` 包）用真实 Chromium 驱动 `source` 提供的合成门户，只依据**可见页面**与
**页面触发的下载**取得原件。门户没有批量数据接口，`/__admin/*` 仅用于操作员布置演练情形，
采集端任何判断都不读取这些控制入口。

## 一、状态机

```
RECORDED                已登记需求，尚未在门户操作
  └─ 上下文卡片三项不符 → CONTEXT_MISMATCH（阻止提交，不消耗额度）
  └─ 提交且页面确认受理 → CLAIMED（申请号以申请记录为准）
  └─ 提交结果无法确定   → CREATE_PENDING（禁止再次点击，先查申请记录）
CLAIMED
  ├─ 申请记录中只有手工申请      → PENDING_VERIFICATION（不认领，留给操作员）
  ├─ 同三元组多条记录/申请号冲突 → PENDING_VERIFICATION
  ├─ queued                     → CLAIMED（排队卡片只代表受理，不代表收齐）
  └─ ready 且逐册下载
        ├─ 门户文件集合 = 已保存原件 → COLLECTED
        └─ 只拿到部分册             → PARTIAL（保留已得部分与缺册原因）
门户行为异常且从未推进 → BLOCKED；已推进过的异常保持原状态，下轮自愈。
```

## 二、不重复扣额的依据（门户无幂等键）

1. **上下文卡片是唯一的创建闸门**：标题先变、卡片后确认。必须等本轮两次 `/context`
   往返都返回且 `data-ready=yes`，解析出的企业代码、报告期、披露范围与申请完全一致才允许点
   “申请导出”。同名企业（C01 集团 / C02 单体）由此被硬性区分。
2. **创建结果不确定绝不自动重试**：断连时 Chromium 会重试 POST，第一次可能已创建并扣额、
   重试才收到 409。因此 409 不作为“未受理”，而作为“可能已生效”的不确定信号，状态停留
   `CREATE_PENDING`，并把 409 记为持久在办闸门（`saw_busy_guard`）。
3. **恢复先认记录再决定动作**：按 `(企业代码, 报告期, 披露范围)` 三元组匹配申请卡片，
   绝不按“最新一条”认领。能确定归属就接着等、从同一申请下载，不要求重新申请。
4. **唯一一次证据补建的条件**：列表已刷新、无同三元组记录、无任何 queued 卡片、
   409 在办闸门已解除（出现过 ready 卡片），且本需求从未补建过（`rebuild_count` 上限 1）。
   不满足任一条件就保持 `CREATE_PENDING` 交操作员；即使误判补建，门户的 409 也保证不产生第二个申请。
5. **手工申请保留**：`actor=operator` 的卡片自动化不认领、不下载，标记 `PENDING_VERIFICATION`。

## 三、下载与原件纪律

- 下载地址短时有效且绑定浏览器会话：只点击申请卡片上渲染出的 `a[download]`，cookie 随浏览器上下文。
- 地址过期（410）或某册暂不可用（503，浏览器表现为 download 被取消）时，记录缺册原因，
  下一轮从**同一申请**重新领取地址，绝不另开申请。
- 每份原件落盘后解析册内声明，`application/company/year/scope` 必须与申请一致，
  并记录 sha256、字节数；逐册原子落盘（`.part` 替换），中断也保留已取得部分。
- 只有门户该申请卡片给出的册别集合是已保存原件集合的子集且逐册校验通过，才报告 `COLLECTED`；
  否则 `PARTIAL` 并在交接单列出缺册与原因。

## 四、暂停、接手与证据

- 每一步状态变更都原子写入 `state.json`（临时文件 `os.replace`）；`pause` 子命令写入
  `PAUSE` 控制文件，运行端在当前需求处理完后安全停下，也可直接中断进程。
- 新进程用同一工作目录即可接手：已受理的需求从申请记录继续等待/下载，不会重新申请。
- 每个需求每轮保留上下文卡片、申请记录、领取地址后的页面 DOM 快照与截图（`evidence/`），
  网络层仅留存页面实际发出的请求路径与状态作为佐证。

## 五、工作目录布局

```
<workdir>/
  state.json                 状态机事实（原子写入）
  PAUSE                      存在即请求安全暂停
  originals/<需求键>/         按申请号-册别命名的原件
  evidence/<需求键>/          页面 HTML 快照与截图
  handover/
    summary.md / summary.json
    <需求键>/manifest.md / manifest.json   区分“门户已确认/尚未确认”
```

## 六、交接单如何区分确认程度

`manifest` 中“门户已确认”只列有页面/原件证据支撑的结论（申请号来自申请记录卡片、
原件经册内声明与哈希校验）；“尚未确认”列出创建不确定、手工申请待核实、缺册原因等，
不把排队卡片说成资料收齐，也不承诺无条件自动重试。
